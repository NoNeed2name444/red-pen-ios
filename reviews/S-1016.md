### R2. opus-job.yml:112-142: the model can read the Anthropic key from /proc (this predates the branch; it came in with 1d85b6ac)
The step's bash is started with ANTHROPIC_API_KEY (and BRIEF) in its environment. `unset` keeps them out of what children inherit, but not out of /proc/<pid>/environ. That bash stays alive as Claude Code's parent. The model is root, the same uid, and reading environ needs no ptrace attach, so Yama's ptrace_scope=1 does not stop it.

I showed this here with a dummy variable, never a real key: `env DUMMY=x bash -c 'unset DUMMY; sh -c "...grep -c ^DUMMY= /proc/$PPID/environ"; true'` prints 0 for the child's env and 1 for the parent's environ.

Fix: end the step with `exec`, so Claude Code replaces that shell. Report in a step of its own.

old (112-142): the whole "Run the job" step.
new:
```
      - name: Run the job
        id: run
        continue-on-error: true
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          BRIEF: ${{ inputs.brief }}
        run: |
          # The key goes to Claude Code on descriptor 3, a pipe it reads once.
          # This shell was started with the key and the brief in its
          # environment, and /proc/<pid>/environ keeps them whatever unset
          # does, so the step ends in exec: Claude Code takes this shell's
          # place, and no process the model can read holds the key.
          key="$ANTHROPIC_API_KEY"; unset ANTHROPIC_API_KEY
          exec 3< <(printf '%s' "$key"); unset key
          git config --global user.name "github-actions[bot]"
          git config --global user.email "41898282+github-actions[bot]@users.noreply.github.com"
          # The workflow's own files and the model's scratch files live apart.
          job="$RUNNER_TEMP/job"; scratch="$RUNNER_TEMP/scratch"; mkdir -p "$job" "$scratch"
          printf '%s\n' "$BRIEF" > "$job/brief.md"; unset BRIEF
          rule="<line 126, unchanged>"
          export CLAUDE_CODE_API_KEY_FILE_DESCRIPTOR=3
          exec claude -p "$(cat "$job/brief.md")" --append-system-prompt "$rule" \
            --model "$MODEL" --effort "$EFFORT" --max-budget-usd "$BUDGET" \
            --permission-mode acceptEdits --allowedTools "Bash,Read,Edit,Write,Glob,Grep" \
            --output-format json > "$job/result.json" 2> "$job/err.txt"
      - name: Report the run
        env:
          outcome: ${{ steps.run.outcome }}
        run: |
          job="$RUNNER_TEMP/job"
          if jq -e . "$job/result.json" >/dev/null 2>&1; then
            jq -r '"cost_usd=\(.total_cost_usd) turns=\(.num_turns) subtype=\(.subtype) outcome='"$outcome"'"' "$job/result.json" | tee -a "$GITHUB_STEP_SUMMARY"
            { echo; echo '```'; jq -r '.result // ""' "$job/result.json" | head -c 3000; echo; echo '```'; } | tee -a "$GITHUB_STEP_SUMMARY"
          else
            echo "::error::no result from Claude Code ($outcome)"
            tail -n 20 "$job/err.txt"
          fi
```
`continue-on-error` lets the report and the bundle steps run after a failed run, as `set +e` did. The subshell behind `<(...)` exits as soon as the key is in the pipe.

### R3. opus-job.yml:184: the push job takes the base from the artifact, which the model can rewrite
9c161c24 keeps the base as a step output, and the bundle step reads it from there (:144-147). But the bundle step and upload-artifact run in the model's container after the model. As root, it can put a `git` ahead of /usr/bin on PATH, or write BASH_ENV into $GITHUB_ENV, and so rewrite `opus-out/base`. The push job then checks against whatever `in/base` says (:184).

Any commit GitHub serves by hash that builds on the branch tip (another branch's, for instance) would then be pushed without the scope, binary or key checks. The model's own new commits cannot get through this way, because they are not on GitHub. The fix is to pass the step output to the push job as a job output.

### R4. opus-job.yml:202-204: the checks see the net diff, not each commit (this predates the branch)
`git diff "$base" job` compares two trees. A key, a binary or an out-of-scope file that one commit adds and a later commit removes is pushed in the public history and never seen. Commit messages are pushed too, and they are never searched for keys.

old:
```
          done < <(git diff --no-renames --name-only -z "$base" job)
          if git diff --no-renames --numstat "$base" job | grep -q '^-'; then echo "::error::a binary file changed; the session adds those itself"; bad=1; fi
          if git diff "$base" job | grep -qE 'sk-ant-[A-Za-z0-9_-]{16}|gh[pousr]_[A-Za-z0-9]{20}'; then echo "::error::the diff looks like it holds a key"; bad=1; fi
```
new:
```
          done < <(git log --no-renames --name-only -z --format= --diff-merges=first-parent "$base..job")
          if git log --no-renames --numstat --format= --diff-merges=first-parent "$base..job" | grep -q '^-'; then echo "::error::a binary file changed; the session adds those itself"; bad=1; fi
          if git log -p --format=%B --diff-merges=first-parent "$base..job" | grep -qE 'sk-ant-[A-Za-z0-9_-]{16}|gh[pousr]_[A-Za-z0-9]{20}'; then echo "::error::a commit looks like it holds a key"; bad=1; fi
```

### Evidence: check 4, the rest of the workflow, and what holds
- Every input reaches a script through `env:` (:77-81, :115, :171-172). None is pasted into a script with `${{ }}`. The brief goes in with `printf '%s\n'` and out with `"$(cat ...)"`.
- The scope loop runs under `set -f` and compares quoted strings (:182, :196-199). A scope of `.`, `/` or `*` covers nothing.
- `bash -e` without pipefail is on purpose (:57-61): `grep -q` decides at :203-204. The cost is that a failing `git` there, or in the `< <(...)` at :202, would read as "nothing found". :189-192 check base and job first, so I am not asking for a change.
- No write token in the work job: `contents: read` (:74-75), `persist-credentials: false` (:96). The token reaches only the push job, which runs on a fresh runner (:163-209), and it pushes without force.
- Open, not a repair: "Delete the bundle" runs `if: always()` (:211). When a check or the push fails (say the branch moved meanwhile), the run's commits are deleted with the bundle. That is the loss 9c161c24 meant to stop, by another road.
